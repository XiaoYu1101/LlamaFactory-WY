## 1. 一期目标与范围

在现有默认架构的 Gradio WebUI 中新增“意图分类”页面，实现：

1. 用户配置类别标识、名称、说明和样例。
2. 调用用户选择的模型，按独立批次生成分类数据。
3. 人工查看、修改、删除、审核生成结果。
4. 将审核通过的数据保存为固定版本，使用内置参数启动现有微调流程。
5. 继续使用原有训练进度、日志、损失曲线、结果和基础评测入口。

一期默认单条文本对应一个意图标签，单机部署、一个共享工作区。暂不引入多标签分类、复杂权限审批或分布式生成。前端按最新要求使用 Ant Design；高级训练页面继续保留，意图业务入口使用统一预设，无需用户逐项填写微调参数。

日常开发及计划提交在 `dev`；`main` 当前仅作项目说明。未经用户另行要求，不向 `main` 合并业务代码。

## 3. 页面与用户流程

新页面包含四个区域：项目与意图配置、生成任务、样本审核、数据版本与开始微调。

### 3.1 配置

- 项目：名称、用途说明、选择的模型及其配置。
- 意图：不可混淆的唯一标识、显示名称、说明、至少 1 条样例、目标数量。
- 校验：标识唯一、名称与说明非空、样例去除空白后非空、数量为正整数。
- 类别说明建议注明与相邻类别的边界，样例支持多行逐条输入。
- 总量模式默认均分到各类别，余数按固定顺序分配，开始前显示实际各类配额；也支持逐类数量。
- 类别定义和生成配置保存为版本；生成任务固定引用开始时的版本。

第一版不在界面暴露提示词、温度等实现参数。生成参数和训练预设由服务统一维护，完整有效配置会随任务保存，便于复现。

### 3.2 数量含义

“生成 N 条”指新增 N 条通过结构检查、空值检查和去重的待审核数据，不包含原始种子样例，也不保证 N 条最终都获人工通过。

分别统计请求产出数、有效新增数、重复数、异常数、待审核数和已通过数。审核拒绝或删除后不自动生成，用户可以按类别发起补生成任务。

用户样例以 `source=user` 保存，可人工审核后纳入训练；不得无提示计入模型生成数量。

## 4. 数据生成设计

### 4.1 模型与独立批次

默认使用所选、具备指令遵循能力的模型生成，生成模型与微调模型可以是同一模型。纯预训练 Base 模型的输出格式和效果需先验证，不能默认可直接承担此任务。

每个生成任务记录模型路径、模型版本信息（可取得时）、对话模板、是否使用适配器以及采样配置，避免静默使用 Chat 页面之前加载的其他模型或微调适配器。

每批步骤：

1. 按类别剩余配额选择本批目标类别。
2. 从用户种子或人工通过的样例中，最多选择 2 条；只有 1 条则使用 1 条。
3. 构造新请求：生成规则、目标类别说明、必要的类别边界、种子样例、本批表达方式和所需数量。
4. 每批最多生成 10 条，最后一批使用实际剩余数量。
5. 请求只返回 JSON 文本数组；目标标签由服务端绑定，不让模型随意添加标签。
6. 解析、校验、去重、原子保存批次和样本，再更新进度。
7. 下一批重新创建 messages，不继承上一批聊天历史，也不发送完整已生成数据集。

目标 1000 条时，在每批恰好产出 10 条有效数据的情况下约需 100 批；去重和失败补齐会增加批数。

### 4.2 上下文与质量控制

- 根据实际 tokenizer、对话模板和输出预算检查单批长度；样例、类别说明设置长度上限。
- 大量类别只提供必要的紧凑边界信息；无法容纳时显示可操作的提示，不能无限拼接类别说明。
- 轮换口语、书面语、短句、完整描述及不同业务情境，降低同一种表达的重复。
- 种子默认不取未经审核的生成结果。只有一条种子时照常运行，但不承诺能产生足够丰富的分布。
- 一期采用 Unicode 规范化和空白规范化后的精确去重；规范化用于比较，保留原文本，不随意删除业务数字或标点。
- 同文本同标签不重复入库；同文本不同标签进入冲突列表，必须人工解决后才能导出。
- 相似改写可能仍通过精确去重。近似重复先由人工审核，语义去重作为后续增强，不称一期已经实现。
- JSON 可仅剥离外围代码块后解析；不执行模型返回的代码，不用 eval 处理输出。
- 若响应包含部分有效条目，可保存通过校验的条目并记录失败原因；批次超额只取当前剩余配额。
- 格式合格仅表示进入待审核状态，语义正确性由人工确认。

### 4.3 任务与恢复

采用独立于浏览器连接的后台任务执行器，界面按任务 ID 查询进度。状态为 queued、running、pausing、paused、completed、failed、cancelled、interrupted。

- 每批成功提交后才能增加有效数量；样本、批次和计数在同一数据库事务内保存。
- 暂停在当前批结束后生效；停止保留已提交数据。当前请求超时及无法返回的情况有明确处理。
- 初始拟定每批最多额外重试 2 次、连续 5 批无有效新增则停止；同时设任务尝试上限，防止长期接近零产出的循环。参数集中配置。
- 批次使用唯一 ID；重复回调或恢复重试不会重复计数、重复插入。
- 重启后将遗留 running 状态改为 interrupted，用户继续任务时按数据库的已提交数据计算剩余量。
- 一个项目同一时间只运行一个生成任务，一张共享设备同一时间只允许一个占用模型资源的任务。
- 不给出未经实机验证的固定速度或完成时间承诺。

## 5. 存储与审核规则

使用 Python 自带 SQLite，第一版无需单独部署数据库。数据库访问使用参数化语句、短事务和样本版本号；后台生成与页面编辑分别使用连接。

建议实体：

| 实体 | 主要内容 |
| --- | --- |
| projects / project_versions | 项目、版本化类别配置与模型选择 |
| intents / seed_examples | 稳定类别 ID、标识、名称、说明、用户样例 |
| generation_jobs / generation_batches | 配额、状态、配置快照、种子 ID、进度、错误与重试 |
| samples | 原文、当前文本、意图、来源、审核状态、删除标记、内容指纹、编辑版本 |
| review_events | 操作前后内容、通过或驳回、时间、备注 |
| dataset_versions / dataset_version_samples | 固定成员及内容、标签映射、导出文件和校验摘要 |
| training_links | 数据版本、训练输出目录、模型与实际训练配置 |

审核页支持分页、关键词、类别和状态筛选；选中行的批量操作只作用于明确选中的样本 ID，不默认扩展到所有筛选结果。

- 状态：pending、approved、rejected；删除使用软删除标记，可恢复。
- 编辑文本或标签会撤销原批准状态，重新进入 pending。
- 恢复已删除样本后重新审核；人工新增样本也进入 pending。
- 修改类别定义创建新项目版本，新版本的数据需重新确认；不追溯改变历史冻结数据和已启动训练。
- 导出检查无未处理待审核项、无未解决标签冲突、训练目标类别均有已通过样本；已驳回或删除记录不参与导出。
- “完成审核”先生成数据版本；“开始微调”消费该固定版本，不直接读取可变审核列表。

建议运行文件保存在可配置的数据根目录，如 `workspace/intent/`；数据库、生成原始响应、导出数据、日志和模型权重加入忽略规则。只将功能代码、空配置示例和文档提交到 Git。

## 6. 数据导出、微调与评测

### 6.1 导出格式

采用已有 Alpaca 格式，输出稳定的类别标识：

```json
{
  "instruction": "判断文本意图。refund_query：查询已申请退款的进度；cancel_order：取消尚未完成的订单。只输出一个类别标识。",
  "input": "我的退款什么时候能到账？",
  "output": "refund_query"
}
```

从配置生成统一分类提示词，保存提示词、类别定义和样本快照。训练、评测及实际推理使用一致的标签和提示格式。审核记录、生成提示和内部来源字段不混入训练答案。

每个版本独立保存训练数据、可选评测数据、dataset_info.json 和 manifest.json，避免改写上游示例数据登记文件。导出采用临时文件写完后原子替换，失败时不发布半成品版本。

### 6.2 训练预设与资源管理

默认 SFT + LoRA。预设采用现有参数作为起点：学习率 5e-5、3 个 epoch、LoRA rank 8、梯度累积 8、截断长度 2048。以上是实施初始值，不是已验证最优配置；批大小和精度在运行机器上检测并验证后确定。

由模型决定对话模板；不静默沿用之前选择的适配器，默认创建本项目的新适配器。对意图短标签任务使用明确的仅输出标签规则，并处理模型模板中的 thinking 配置，避免将推理过程混入标签。

当前训练页验证集比例默认为 0，不能因此承诺训练期间自动有评测结果。训练前核对实际数据数量和评测来源。

一次启动流程：校验固定数据版本 → 获取设备独占权 → 停止生成并卸载推理模型 → 填入原训练页面输入 → 启动现有 Runner → 显示原训练页状态与结果。

设备资源协调需覆盖新生成入口以及原 Chat 的加载、卸载、对话和 Train/Evaluate 启动入口，避免只锁住新页面而让原页面绕开。启动锁在提交任务前获取，并在异常、停止和完成时释放。

所有训练保存固定数据版本 ID、模型路径、实际参数和输出目录。训练输出目录以项目及运行 ID 区分，不覆盖之前结果。

### 6.3 基础评测边界

一期复用原有 Evaluate & Predict 页面及指标。源码中的 ROUGE/BLEU 是文本生成相似度，ComputeAccuracy 是 token 级准确率，均不直接代表样本级意图分类准确率。

优先使用用户另外提供、人工确认的真实测试数据，测试数据不参与生成种子和训练。没有独立测试集时，只能将合成留出集标为内部检查；划分时按种子来源或相似组隔离，避免相近改写同时进入训练和评测。类别样本不足以划分时如实显示，不生成虚假的评测结果。

后续如需要，可基于原预测文件增加标签完全匹配准确率、各类 Precision/Recall、Macro-F1 和混淆矩阵；不作为一期已有能力承诺。

## 8. 分阶段执行与验收

| 阶段 | 工作内容 | 完成标准 |
| --- | --- | --- |
| P0：仓库与方案 | 恢复 main 项目说明，dev 保存源码、README 和本计划 | 分支清晰、源码可追溯，未把计划功能写成已实现 |
| P1：配置与审核基础 | 数据模型、SQLite、项目和意图表单、人工样本录入及审核 | 重启后可恢复；一条样例可配置；编辑后审核失效；删除及恢复规则正确 |
| P2：分批生成 | 对话适配、独立提示、配额、去重、任务进度与恢复 | 使用模拟模型完成 1000 条；历史不累积；异常、重复、暂停恢复不丢数据、不误计数 |
| P3：数据到训练 | 冻结导出、预设、设备协调、原 Runner 衔接 | 待审核数据不能进入训练；一次点击启动；原训练页显示结果；旧数据版本不被修改 |
| P4：实机验证 | 指定真实模型与设备，验证生成、审核、小规模训练和原评测 | 完整走通一轮，并记录模型、显卡、实际配置、耗时和遇到的限制 |

当前从 P1 开始安排开发，先建立可持久化的数据及审核闭环，再接模型生成。没有真实 GPU 或可用模型时，可以完成 P1、P2 的模拟测试及 P3 的导出/参数衔接测试，但不得宣称实机微调已经通过。

### 关键验收用例

- 一个类别只有一条样例时仍可运行；零样例、重复类别标识和非法数量有明确提示。
- 每批最多引用两条合法种子；模型请求长度不会随总批次数增长。
- 目标不是 10 的倍数时不超额；重复和格式错误不被计为有效新增。
- 同文本不同标签不能自动通过审核或进入导出。
- 部分批次失败、关闭页面、进程重启后，已提交数据仍在且能继续。
- 在暂停、删除、编辑和批量审核的交叉操作下，状态、数据和计数一致。
- 编辑 approved 样本必须重新审核；冻结版本不随编辑变化。
- 数据目录和 dataset_info 可被现有数据加载器读取；分类答案与标签配置一致。
- 生成、Chat 和训练争用同一设备时正确排队或提示；失败后锁释放。
- 原 Train、Evaluate & Predict、Chat 的主要事件连接仍可正常工作。
- 使用 `WANDB_DISABLED=true` 执行相关测试；代码变更按项目规则运行相关 Ruff 和许可证检查。文档修改只做内容、链接及差异检查。

## 9. 实施前需要落定的环境信息

模型文件或模型名称、模型是否支持指令对话、运行系统、GPU 型号及显存、是否有独立测试数据。这些信息不阻塞数据管理和模拟生成开发；开始实际模型加载及训练验证前必须确认。

暂不预估 1000 条生成耗时与最终分类效果，待真实模型试跑后以实测数据为准。
